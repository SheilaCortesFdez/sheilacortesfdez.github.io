Backend · Batch · Architecture

Desarrollo de un batch Java 17 con arquitectura hexagonal

Desarrollo desde cero de un proceso batch en Java 17 utilizando arquitectura hexagonal para procesar información de Ebury, aplicar reglas de negocio, consultar cuentas, validar los datos y generar los ficheros requeridos por el sistema consumidor.

Contexto

El proceso trabaja con información recibida de Ebury y debe generar una única fila por cada J en el fichero de salida. Una misma entidad puede estar representada por una J master y varias Js relacionadas como primos.

Agrupación de Js

Cuando una J tiene registros relacionados, los atributos EBATT0061 y EBATT0062 identifican la J master a la que pertenece cada primo.

El proceso agrupa las Js relacionadas bajo su J master y realiza el sumatorio de EBATT0063 (Total EUR Net Profit) de todos los registros que forman parte de la misma agrupación.

El resultado se representa en una única fila correspondiente a la J master.

Control del dato recibido

Para EBATT0063 se utiliza el registro correspondiente al fact_last_update más reciente dentro del mes de ejecución, contemplando que pueda existir más de un registro recibido durante ese periodo.

Selección de cuenta

Para obtener el idContract, el proceso consulta el API de cuentas pasivas buscando cuentas activas en euros correspondientes a los productos:

  • 300 — Cuenta Corriente
  • 301 — Cuenta de Ahorro

De las cuentas obtenidas se selecciona aquella que presenta el mayor saldo.

Reto de rendimiento

Una J podía tener un volumen elevado de cuentas y el API utilizado trabaja mediante paginación. Las consultas podían provocar que el gateway superase su límite de 30 segundos.

Para resolver este problema se incorporó paralelización en la recuperación de las diferentes páginas, reduciendo el tiempo necesario para obtener la información y evitando los timeouts del gateway.

Validación de integridad

El total calculado a partir de los valores de EBATT0063 se compara con el valor de BSFCT017 — Total EUR Net Profit.

El proceso únicamente continúa cuando la diferencia se encuentra dentro de un margen de tolerancia de ±1%.

Si existe una discrepancia superior al margen permitido, se genera una notificación por email para solicitar la corrección y el proceso no continúa.

Generación de ficheros

Una vez superadas las validaciones, el proceso genera dos ficheros CSV con los requisitos de formato definidos por el sistema consumidor.

Los ficheros se generan utilizando CP1145 y representación hexadecimal, debido a los requisitos de integración del sistema destino.

Distribución

Si el proceso finaliza correctamente, los ficheros se envían por email a los destinatarios correspondientes y se depositan en un SFTP.

Posteriormente, Control-M realiza el envío hacia el servidor del sistema consumidor.

Arquitectura

El desarrollo se realiza con Java 17 y arquitectura hexagonal, separando la lógica del proceso de las integraciones externas.

Backend · APIs · B2B Integration

API de integración de partners y gestión de leads

Diseño y desarrollo desde cero de una API destinada a integrar diferentes partners con una entidad bancaria, permitiendo gestionar sus leads mediante una interfaz común y segura.

Contexto

La entidad bancaria trabaja con diferentes partners con los que mantiene acuerdos comerciales. Cada partner dispone de un identificador único y de una configuración propia de productos, atributos y steps asociados a sus leads.

El proyecto nació para sustituir el modelo anterior de integración basado en el intercambio de ficheros CSV mediante SFTP por una integración basada en API.

Integración mediante API

La API proporciona tres operaciones principales para gestionar el ciclo de vida del lead:

  • Alta de lead
  • Actualización de atributos
  • Actualización de steps

Autenticación

Cada partner dispone de unas credenciales propias mediante Client ID y Client Secret, utilizadas para obtener el token de acceso mediante OAuth 2.0.

Configuración por partner

La integración debe contemplar las particularidades de cada partner, incluyendo los productos, atributos y steps definidos en el acuerdo correspondiente.

Ciclo de vida del lead

Los leads recibidos a través de la API deben avanzar por los diferentes steps definidos hasta alcanzar el estado ganado, momento necesario para que puedan entrar en el proceso de facturación.

Stack técnico

Java Spring Boot REST OAuth 2.0 API B2B
Backend · Microservices · KYC

Automatización de un proceso KYC

Contexto

Desarrollo desde cero en Java 17 de los microservicios necesarios para automatizar un proceso KYC dentro del flujo de onboarding. Cuando un lead alcanza el punto correspondiente del proceso, se ejecuta la lógica necesaria para obtener la información requerida y devolverla al partner.

Integración entre servicios

El proceso coordina diferentes microservicios y APIs para obtener la información asociada al lead y construir la respuesta necesaria. Se implementaron las llamadas entre servicios teniendo en cuenta tanto los tiempos de respuesta como los posibles errores durante la comunicación.

Resiliencia

Se incorporó Circuit Breaker junto con mecanismos de fallback para evitar que un servicio lento o no disponible afectase al resto de la aplicación.

Además, cuando uno de los servicios devuelve un valor nulo, el flujo continúa sin lanzar una excepción y se mantiene el valor correspondiente en la respuesta.

Paralelización

Para reducir el tiempo total de respuesta se eliminaron determinadas paginaciones y se paralelizaron las llamadas a los diferentes servicios implicados en el proceso.

Validaciones

Se implementaron validaciones sobre la información obtenida para comprobar que los datos corresponden al lead procesado y determinar si debe ejecutarse el flujo KYC.

Resultado

El proceso permite automatizar la obtención y devolución de la información KYC dentro del flujo de onboarding, integrando varios microservicios de forma resiliente y optimizando el tiempo de ejecución mediante paralelización.

Entrega y operación

Además del desarrollo, realizo las subidas a los diferentes entornos y gestiono los Pull Requests, incluyendo la revisión de los cambios realizados por otros compañeros.

Los pods están desplegados en OpenShift. Para analizar la ejecución de los servicios y resolver incidencias revisamos los logs de los pods y utilizamos Dynatrace.
